# Specialist modules

Select by the decision at risk, not by a fixed sequence. Each domain has a standalone skill and a local fallback module. Use the common company context and claim/objection IDs; never create inconsistent private definitions inside a review.

For a focused request, read the matching standalone skill through the environment's normal skill mechanism if available. Otherwise use the local module below. Either route works independently; do not run both or automatically expand a narrow test into a full review. Names identify optional skills, not required filesystem paths.

## Routes by common artifact

For Seed/Series A or foundational questions about problem strength and venture potential, start with [early-stage-gates.md](early-stage-gates.md). The two standalone companion skills can run before a fundraising package exists; their outputs feed the relevant nine modules without duplicating the evidence collection.

- GTM strategy, CRM/channel exports or pilot/cohort pack: GTM; add only the product, business-model, capacity or cash dependencies needed to answer the question.
- Deck: cold comprehension, then the modules driving its material claims. A strong narrative does not validate an unseen model.
- Financial workbook: financial model + business model; add scalability for growth assumptions and market for opportunity/penetration limits.
- Product/technical pack: product/technology; add business model for cost-quality tradeoffs, competition for claimed advantages, and scalability for load/deployment claims.
- Market/category paper: market + category/timing + competition; add financial model only where a return or financing claim is made.
- Full growth data room: screen all nine and deepen the material gaps; distinguish missing coverage from observed failure.
- Founder practice: start with the most material unresolved objection or the requested module, then follow dependencies. It need not begin at market size.

## Common handoff

Each reviewed module contributes: tested claims, strongest supported point, material objection(s), evidence status, exact source, test result or unexecuted test plan, required change, and dependencies. Return a compact module assessment rather than a separate long memo unless requested.

Combine duplicates by causal issue. For example, heavy human review may appear in product reliability, delivery cost, staffing capacity, and cash. Record its consequences in each domain but do not count it as four independent discoveries or repeatedly request the same data.

For portfolio work, reuse the method, never another company's facts. Cross-company comparisons require comparable definitions and authorization to use the records.

## Standalone operation and coordination

The nine specialists are independent entry points for domain reviews. Each includes its own evidence method, stage calibration, domain tests and outputs. The master retains local fallback modules for portability and reconciles the results when a full or multi-domain review is requested.

The two foundational companions remain independent: customer-problem-stress-test for problem/discovery evidence and venture-scale-assessment for potential, round readiness and mandate fit. Use the fallback in [early-stage-gates.md](early-stage-gates.md) if they are unavailable.

Use the eleven specialists selectively. The user may upload a full room and ask only for a moat challenge, runway check or category test; the volume of supplied material does not expand the requested scope. Reuse completed evidence and disclose material dependencies. Do not require eleven reviews to answer one question.
